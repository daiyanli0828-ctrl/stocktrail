# 双模型开发评审工作流

> 本工作流从 M0 第一个功能点（F-01）开始执行，每个功能点独立走完一轮"开发 → 自测 → 评审 → 修复/确认"。

## 1. 角色与分工

| 角色 | 承担者 | 职责 | 产出物 |
| --- | --- | --- | --- |
| 开发 | deepseek-v4-flash | 认领功能点 → 按开发规格实现 → 按自测清单逐条自测 → 提交 | 代码 + `reviews/F-xx-自测.md` |
| 评审 | deepseek-v4-pro | 按评审检验逻辑逐项核对（A 代码级 / B 数据级 / C 行为级 / D 一致性）→ 输出结论 | `reviews/F-xx-评审.md` |
| 确认 | 用户本人 | 产品形态与价值观类功能点亲自确认；仲裁分歧；批准变更申请 | 看板备注 / 变更批准记录 |

## 2. 功能点生命周期流程

```
1. 认领   开发方从看板领取 pending 功能点 → 状态 in_dev
2. 实现   严格按《02-M0功能点开发规格与评审检验》中该功能点的"开发规格"实现
3. 自测   逐条执行该功能点的"自测清单"，产出自测记录 → 状态 self_tested
4. 评审   评审方逐条执行"评审检验逻辑"，产出评审报告 → 状态 in_review
5. 结论   三种：
   · 通过（passed）          → 状态 done，进入下一功能点
   · 打回（rejected）        → 列出问题清单 → 开发方修复 → 回到步骤 3（自测版本号 +1）
   · 带条件通过（conditional）→ 列出条件（通常为"运行时核对项/用户确认项"）→
                               开发方补齐证据或用户确认后 → passed
6. 用户确认  产品形态与价值观类功能点（如 F-06 日报渲染、F-11 财联社）必须经用户
            亲自确认后才 done；纯技术点（如 F-01、F-03）可跳过此步
```

## 3. 评审检验逻辑的四级检查（每个功能点都按此组织）

| 级别 | 含义 | 检查对象示例 |
| --- | --- | --- |
| **A 代码级** | 代码本身可静态/动态判定的事实 | 字段是否存在（adj_close、reason_recorded_at）、阈值表与文档一致、无硬编码判据、无 Web 栈依赖 |
| **B 数据级** | 需要与真实数据/手工核算对照 | 抽 N 条行情与行情软件核对、账户体检与 Excel 手算一致、构造测试样本验证边界 |
| **C 行为级** | 输出内容与行为护栏/价值观的一致性 | 交易频次行在位、无标的清单、无指令式用语、"无需操作"正常渲染、破止损位提示不含新建议 |
| **D 一致性** | 与企划 v1.0 冻结基线的符合性 | 对应条款引用是否被满足、无已否决方案残留（加权评分/星级/午报/盘中） |

## 4. 评审结论与整改规则

- **通过（passed）**：四级检查全部通过；评审报告逐项附证据（文件路径/行号/运行输出片段）。
- **打回（rejected）**：任一检查项不通过。报告必须给出：问题清单（每条含检查项编号、现象、期望、修复建议）。开发方修复后重提，自测与评审版本号 +1（如 F-07 第 2 轮自测）。
- **带条件通过（conditional）**：主体正确但存在"只能在真实运行中验证"的项（如连续 5 交易日成功率）。条件必须可执行，并写明由谁（开发方/评审方/用户）在何时（第几个交易日）复核。
- 评审报告不得出现"整体感觉不错"类结论；每条检查都要有 是/否 与证据。

## 5. 产物落盘规范

- 自测记录：`docs/dev/reviews/F-xx-自测.md`（模板见《04-评审报告模板》§自测记录模板）
- 评审报告：`docs/dev/reviews/F-xx-评审.md`（模板见《04-评审报告模板》§评审报告模板）
- 状态看板：`docs/dev/README.md` 表格实时更新
- 命名：功能点 ID 固定（F-01~F-11），多轮时文件名加轮次后缀（`F-07-自测-第2轮.md`）

## 6. 变更控制

- **先改企划再改代码**：开发或评审发现企划 v1.0 缺陷（如数据源字段与文档不符、验收标准不可执行）→ 在 `docs/dev/变更申请.md` 记录 → 用户批准 → 企划升小版本（v1.1+）→ 按新版本继续开发；
- **评审发现功能点间依赖冲突**（如 F-10 依赖 F-02 的接口但接口未定）→ 评审报告中标注，排期时处理；
- **范围护栏**：任何"顺手实现"的 M0 清单外功能，评审方按 D 级检查直接打回。

## 7. M0 退出评审（第 3 周，由 v4-pro 主持）

M0 全部功能点 done 后，做一次整体评审，依据：
1. 连续 20 个交易日生成成功率 ≥ 90% 且每日有 read 记录（C16/C17）；
2. 逐源成功率记录，任一源 < 80% 已解决或换源；
3. 按 C5 第 8 条产出段落跳过率报告，跳过率 > 50% 段落列入删除清单；
4. 输出《M0 价值回顾报告》：哪段被读、哪段被跳、行为指标（按计划执行率/非计划笔数）初值；
5. 据以上数据，向用户提交下一阶段优先级建议（从《03-M0后功能点…》价值清单中选取）。
