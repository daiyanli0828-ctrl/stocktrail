# 开发文档空间（docs/dev）

> 本空间是**开发阶段的唯一工作台**：每个功能点的开发规格、评审检验逻辑、自测记录、评审报告都在这里落盘。产品方案基线为企划 v1.0（`docs/01`），开发中任何偏离必须先改企划（小版本 v1.1+），再改代码。

## 空间结构

| 文件 | 内容 |
| --- | --- |
| `01-双模型开发评审工作流.md` | 角色分工（v4-flash 开发 / v4-pro 评审 / 用户确认）、流程、状态机、落盘规范 |
| `02-M0功能点开发规格与评审检验.md` | **M0 全部功能点（F-01~F-11）**：开发规格 + 自测清单 + 评审检验逻辑 |
| `03-M0后功能点开发规格与评审检验.md` | M0 后按价值密度推进的功能点：触发条件 + 规格要点 + 检验要点 |
| `04-评审报告模板.md` | 评审报告统一模板 |
| `reviews/` | 每个功能点的自测记录与评审报告（`F-xx-自测.md` / `F-xx-评审.md`） |
| `变更申请.md` | 开发中发现企划缺陷时的变更申请（批准后走企划小版本） |

## 双模型分工

| 角色 | 承担 | 职责 |
| --- | --- | --- |
| 开发 | **deepseek-v4-flash** | 认领功能点 → 按开发规格实现 → 按自测清单自测 → 提交自测记录 |
| 评审 | **deepseek-v4-pro** | 按评审检验逻辑逐项核对（代码级/数据级/行为级/一致性）→ 输出评审报告（通过/打回/带条件通过） |
| 确认 | **用户本人** | 产品形态与价值观类功能点亲自确认；需求仲裁；变更申请批准 |

## 评审四原则（继承 v0.6 精神）

1. **检验必须可执行**：每条检查都能对照代码/数据/运行结果给出 是/否，禁止"感觉不错"类结论；
2. **一致性**：实现与企划 v1.0 冻结基线一致，偏离先改企划；
3. **价值**：凡是产出给用户看的功能，必须有核对证据或 read 数据支撑；
4. **留档**：所有自测与评审报告永久留在 `reviews/`，可回溯。

## 变更控制

- 企划 v1.0 冻结；开发中发现的缺陷通过 `变更申请.md` 提出，用户批准后按小版本（v1.1+）修订企划，再改代码；
- M0 边界硬约束：两周内只做 M0 清单（F-01~F-11），任何额外想法记入 `03-M0后功能点…` 的价值清单排队；
- 价值验收：段落跳过率 > 50% 直接删除，不做优化、不留开关（C5）。
