# M0 功能点开发规格与评审检验

> 每个功能点固定三段：**开发规格**（给 v4-flash：做什么、输入输出、关键约束）→ **自测清单**（开发方自己先核对）→ **评审检验逻辑**（给 v4-pro：A 代码级 / B 数据级 / C 行为级 / D 一致性逐项检查与通过判据）。
> 依据：企划 v1.0（docs/01）+ 架构 v0.6（docs/03）。术语：后复权价 `adj_close`、行为护栏（C1）、板块分档阈值（D2）。

## F-01 仓库骨架与配置

**开发规格**：
- 目录：`app/{collectors, quality, analyzer, summarize, review}`、`scripts/`、`data/{inputs, processed, calendar}`、`docs/dev/reviews/`；
- config 四件（M0 最小集）：
  - `data_sources.yaml`：仅 akshare 启用；预留自定义源注册结构；
  - `quality_rules.yaml`：分板块涨跌幅阈值（ST 5% / 主板 10% / 创业板·科创板 20% / 新股首日豁免 / 退市整理 10%）+ 除权日豁免开关；
  - `verify_rules.yaml`：预测验证判据占位（F-09 填充）；
  - `signal_rules.yaml`：信号清单占位（M0 不对外输出，F-06 用最小版）；
- `requirements.txt`：akshare、pandas、pyyaml（**无** Web 框架、无 LLM SDK、无 APScheduler——对应 C9/C13/C18）；
- `init_db.py`：建三表（字段严格按架构 §4.5）：
  - `quotes(code, trade_date, open, high, low, close, adj_close, volume, amount, pct_chg, quality_flag)`，唯一索引 (code, trade_date)；
  - `trades(id, code, side, price, shares, ts, reason_type, reason_note, plan_target, stop_loss, reason_recorded_at, post_hoc)`；
  - `notes(id, ts, kind, content, rel_trade_id)`；
- `data/inputs/` 下放置模板：`watchlist.yaml`、`positions.yaml`、`trades.csv`（空模板带字段说明注释）。

**自测清单**：目录齐全；`init_db.py` 可执行；sqlite3 查看三表字段与 DDL 一致；requirements 无违禁依赖。

**评审检验逻辑**：
- A：三表 DDL 与架构 §4.5 完全一致（重点：adj_close、reason 四字段 + reason_recorded_at + post_hoc、notes.kind）；无第 4 张表（D5）；requirements 无 Web/LLM/调度依赖（C9/C13/C18）；
- D：config 四件存在且字段与架构一致；与企划 v1.0 §2.7 M0 范围一致；
- 通过判据：A、D 全部 是。

## F-02 akshare 采集（含复权）

**开发规格**：
- `collectors/base.py`：`DataSourceAdapter` 基类（方法签名统一）；
- `collectors/akshare_src.py`：
  - `get_daily_quotes(codes, start, end)`：返回含 `adj_close`（后复权，akshare 的 qfq 因子），trade_date 存 UTC 日期；
  - `get_index_snapshot()`：主要指数（上证/深证/创业板指等）收盘与涨跌幅；
  - `get_market_breadth()`：上涨家数、下跌家数、成交额、涨停/跌停家数；
- 频率控制：请求间隔 ≥ 0.5s，失败指数退避；失败记录 source 与原因；
- 输出《字段稳定性清单》：记录各接口字段名、单位、空值行为（供 F-03 阈值校准）。

**自测清单**：跑通 3 只股票 × 3 个交易日；adj_close 与不复权 close 两列存在且除权日不跳变；breadth 与指数快照可拉取。

**评审检验逻辑**：
- A：基类存在、akshare_src 实现其接口；adj_close 字段来源是后复权因子（代码注释说明）；无实时/盘中接口（C10）；频率控制代码存在；
- B（数据级，重点）：抽 3 只股票 × 3 个交易日，与行情软件核对 close/pct_chg；其中至少 1 只股票近半年有除权，核对其除权日 adj_close 连续性；涨跌家数/成交额与东财或同花顺核对 1 天；
- D：与企划 §2.5 M1（M0 唯一源 akshare）一致；
- 通过判据：B 核对误差在舍入范围内；《字段稳定性清单》已产出且非空。

## F-03 质量检查三条（分板块阈值 + 复权豁免）

**开发规格**：
- `quality/checks.py` 实现三条，规则全部读 `quality_rules.yaml`（代码无硬编码阈值）：
  1. 价格非法：close ≤ 0 或 adj_close ≤ 0 → 拦截；
  2. 交易日缺数据：本地交易日历（`data/calendar/trading_calendar.yaml`，先手动生成 2026 全年）判定为交易日但无行情 → 标记 + 报告标注；
  3. 涨跌幅超阈值：|pct_chg| > 板块阈值（按股票所属板块：ST 5% / 主板 10% / 创业板·科创板 20% / 新股首日豁免 / 退市整理 10%）→ 标记 + 拦截；
- 除权日豁免：除权日（**分歧公式：当日 |adj 日变动% − close 日变动%| > 0.5%** 视为除权日，见 CHG-001）跳过涨跌幅检查（D1）；
- 拦截/标记落 `quality_logs` 表（临时并入 notes 或建第 4 张表？——按 D5 原则：M0 先并入 `notes(kind=quality)`，M0 后补独立表）；日报底部标注"数据质量：正常 / N 项异常已排除"。

**自测清单**：构造 5 类测试样本逐一验证：正常日（过）、ST 涨 4.9%（过）/ 5.1%（拦）、创业板涨 19.9%（过）/ 20.1%（拦）、除权日（豁免）、新股首日（豁免）、负价（拦）。

**评审检验逻辑**：
- A：阈值只存在于 quality_rules.yaml（grep 代码无 5%/10%/20% 常量）；除权豁免逻辑存在；交易日历本地文件存在；
- B：5 类测试样本行为全部符合预期（评审方复跑或审查自测记录附的输出）；交易日历抽 3 个已知休市日（如春节、国庆）验证"休市日不判缺数据"；
- D：与 D1/D2 完全一致；无"涨跌幅 > 30% 一刀切"旧规则残留（D2 推翻项）；
- 通过判据：测试样本全部符合；grep 无硬编码。

## F-05 账户体检计算

**开发规格**：
- `analyzer/portfolio_health.py`：输入 `positions.yaml`（code/shares/avg_cost/opened_at/stop_loss/plan_target）+ `quotes` 最新收盘 → 输出：
  1. 总仓位 %（持仓市值/总资产，总资产在 positions.yaml 顶部声明）与**档位上限**对比（三档仓位上限 30%/50%/80%，先写在 positions.yaml 或 decision_profiles 占位，属 C2 的"档位=仓位阈值"）；
  2. 单票占比超限项（单票 > 档位单票上限，如 20%）；
  3. 第一大行业集中度（行业映射表简版，先按代码段/手动标注）；
  4. **已跌破自设止损位的持仓**（现价 < stop_loss）——输出措辞："⚠ 600519 已跌破你设定的止损位 X 元（现价 Y），请按你的计划处理"（执行用户过去的决定，不含新买卖建议，C2/C10 兼容）；
  5. 浮盈浮亏分布（按仓位加权的盈利/亏损数量与幅度分桶）；
  6. 持仓平均天数（now - opened_at）。
- 纯函数、可单测。

**自测清单**：构造 2 组持仓（正常组 / 含破止损 + 超集中 + 行业集中组），与 Excel 手工核算一致。

**评审检验逻辑**：
- B：两组构造样本与手工核算一致（仓位%、单票占比、集中度、平均天数、浮盈亏分桶）；
- C（行为级，重点）：破止损位输出措辞含"你设定的止损位""按你的计划处理"，**不含**任何新买卖建议（无"建议卖出/减仓"字样）；整体无指令式用语；
- D：与 C2（账户体检六要素）、C10（止损提示唯一例外）一致；
- 通过判据：核算一致 + 措辞检查通过。

## F-06 daily.md 渲染（行为护栏三要素 + 六部分）

**开发规格**：
- `summarize/render_daily.py`：Jinja2 模板 → `daily.md` 落盘 Obsidian vault 目录（vault 路径可配置）；
- 第一周四部分：市场概况 / 账户体检 / 自选异动 / 交易频次行；第二周加：昨日验证（F-09 数据）/ 明日计划（条件式）；
- **行为护栏三要素（模板层硬性）**：
  - 交易频次行固定显示（读 trades 表统计：本月笔数/上月笔数/换手率/非计划笔数=无对应 note 计划的交易）；
  - 任何段落**不含可买标的清单**（热点段只描述市场结构：资金往哪类资产集中、集中度多高）；
  - "今日无需操作"正常渲染，非异常分支；
- 底部固定：数据质量标注 + 免责声明；
- 全文无指令式买卖用语（无"买入/卖出/加仓/减仓"建议句；自选异动用"上涨原因/风险/当前状态"表述）。

**自测清单**：跑 1 天真实数据生成 daily.md；逐条核对六部分与护栏三要素；数字与 F-04 输出一致。

**评审检验逻辑**：
- C（行为级，重点）：模板/输出中交易频次行存在且位置固定（C1.1）；全文 grep 无标的清单类表述（C1.2）；构造"无触发信号"的输入验证"无需操作"正常渲染（C1.3）；grep 无指令式买卖用语（C7）；
- B：抽 1 天日报数字与行情软件核对；账户体检段与 F-05 输出一致；
- D：六部分结构与企划 §2.5 M3 一致；含免责声明与数据质量标注；
- **用户确认项**：日报版式与措辞风格需用户亲自过目确认（产品形态类）；
- 通过判据：C 三要素全 是 + 数字核对一致 + 用户确认通过。

## F-07 note.py 盘前预先承诺（T+1 锁定 / post_hoc）

**开发规格**：
- `scripts/note.py`：命令行录入——`note buy 600519 --reason 趋势 --target 1700 --stop 1500 --note "突破平台"`；
- 写入 trades：`reason_type ∈ {趋势, 事件, 情绪}`（恰 3 类，C4）；`reason_recorded_at = now`；
- **时间边界（C3）**：
  - 成交 T+1 前（24h 内）允许补充/修改 reason 四字段；
  - T+1（>24h）后代码层拒绝修改（update 被拒或标记锁定）；
  - 晚于成交 24h 首次补录 → `post_hoc = true`；
- 收盘后比对：note 计划 vs 实际成交 → 输出"今日按计划执行 N 笔 / 非计划 M 笔"（供 F-06 频次行）；
- 券商 CSV 导入脚本仅更新成交价/手续费，**不写 reason 字段**（C19）。

**自测清单**：时间边界三场景测试（T+0 可改 / T+1 拒改 / >24h 补录标 post_hoc）；3 类理由枚举校验；计划 vs 成交比对正确。

**评审检验逻辑**：
- A：锁定逻辑存在且可证明（修改被拒的测试证据）；post_hoc 判定正确；reason_type 枚举恰为 3 类（无 5 类残留，C4）；
- B：计划 vs 成交比对构造 2 组场景（按计划/非计划）统计正确；
- D：与 C3（事前锁定+盘前承诺）、C19（CSV 仅对账）一致；CSV 导入脚本无 reason 写入逻辑；
- 通过判据：A/B/D 全通过（附测试输出证据）。

## F-09 昨日验证流水线（prediction 必填 / 判据入 config）

**开发规格**：
- 前瞻结论数据结构：`{conclusion, logic, prediction: {direction, target_scope, deadline}}`——**prediction 缺失的结论拒绝写入日报**（C6）；
- `verify_rules.yaml`：命中判据（示例："次日概念指数相对沪深 300 超额收益 > +1% 记命中"）+ 判据版本号；
- `scripts/verify_yesterday.py`：读昨日结论 + 今日实际 → 计算 verdict（命中/未命中/部分命中/无法判定；M0 规则产出前两者，部分命中预留给多目标判据）→ 写回 `verified_at`；
- 判定日数据未就绪（最新 bar ≠ deadline）时返回"无法判定"并如实标注数据日期，禁止用旧数据静默判定；
- prediction.deadline 参与计算（M0 仅支持 next_day）；prediction.criterion_id 选择判据（默认 price_direction，未注册 → 无法判定）；
- 判据只从 config 读（代码无硬编码判据）；判据每次修改必须升版本号并留记录；
- 日报"昨日验证"段输出：结论、判定、判据原文。

**自测清单**：构造 2 组历史结论（可命中/不可命中）按判据计算正确；prediction 缺失被拒；判据版本记录生效。

**评审检验逻辑**：
- A：prediction 必填校验存在（有测试证据）；grep 代码无判据常量（仅 config 读取）；判据版本号机制存在；
- B：2 组构造样本计算结果正确；
- D：与 C6 完全一致（判据事前锁定——开发过程不得出现"看到结果后改判据"的痕迹，如 git 历史/变更记录）；
- 通过判据：A/B/D 全通过。
